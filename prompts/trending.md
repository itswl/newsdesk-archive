## 硬性约定

1. **`stars today` 是滞后值，约为 24 小时前的速率。** 只用于排序和判断进出榜，**绝不当增量引用**。加速中的项目会被它低估，减速中的会被高估。
2. **新进项目（无基线）不给速率点估计。** 既往 24/24 例新进项目均被页面值低估，所以只能判定「真实速率不低于页面值」。
3. **`停更` 必须读默认分支 HEAD 提交时间，不是 `pushed_at`。** `pushed_at` 会被 fork 推送、tag、CI 等活动刷新，掩盖真实停更。两者差值大的单独列出。
4. **掉榜是否等于真降温，每期都要验。** 拿掉榜项目今日实测速率对比其上期页面值，逐条判定，累计统计成立率，反例必须写出来。
5. **下载量作为第二使用度代理。** 算「下载/星标」比值。注意局限：走 Docker / PyPI / HuggingFace 分发的项目 release 下载为 0 不代表无人使用，必须标注。

## 五节结构

1. **原始榜单** —— 表格：# / 项目(链接) / 语言 / 星标 / f/s / stars today / Δ天 / 实测比页面 / 授权 / 年龄 / 主干停更。表前用一段话交代每列口径。
2. **核心分类** —— 按领域分组，写出每组的共同点，特别是那个共同点是否与 AI 无关。
3. **趋势洞察** —— 4–6 条。**必须做跨期而不只比上一期**：用 `rank_history` 看名次轨迹（爬升
   还是靠单日冲高）、`boards_seen` 看谁是长期在榜谁是一日游、`returning` 找掉榜后回归的案例——
   回归项目往往说明当初的「降温」判断只是短期波动。
   跨期是用来支撑判断的，**不要把每个项目的名次轨迹都列出来**——只写出现了什么模式、由哪几个
   项目佐证。结论不确定的标出需要复核。
4. **重点推荐** —— 1–2 个，每个写核心亮点 + 数据支撑 + **必须先知道的前提/风险**。数据不支持的项目不要推荐。
5. **数据核查** —— 授权异常 / 停更（含 `pushed_at` 掩盖案例编号）/ 掉榜=降温验证 / 上期首推次推追踪 / `created_at` 是否等于项目年龄 / 下载量代理 / 本期方法论缺口。
